# 周报（2026-03-11）

## 本周进展

本周围绕 MagicLens 在 MRAG 场景中的检索与重排能力进行了进一步讨论，并梳理了两条实验线：

- $GT-RAG-RANKING_{magiclens}$：在 GT-RAG 设定下，用 MagicLens 对候选图像进行重排。
- $CLIP-RAG-RANKING_{magiclens}$：在 corpus 检索设定下，先做粗召回，再结合 MagicLens 进行排序与分析。

围绕 corpus 检索版本，目前明确了以下流程设定：

1. 对 corpus 中的图像使用 MagicLens 抽取特征。
   - `instruction=""`
   - 每个 query 先选前 5 个候选
2. 查询端使用 `instruction(问题) + <query_image>` 输入 MagicLens，得到 query embedding。
3. `Incomplete` 场景只有 1 个 GT，重排空间受限，需要单独分析。
4. query / instruction 生成阶段可优先尝试 `gemini-2.5-flash`。
5. 后续补充 `+CLIP` 结果，和 MagicLens 方案并行比较。

## 当前结果与初步判断

- 当前这组实验的 overall 结果约为 `46.3%`。
- 其中 MagicLens 方案结果为 `46.27%`。
- 目前看，单纯依赖相似度做检索或重排，提升有限；后续重点应转向“查询信息”的设计，而不是只做 embedding 相似度匹配。

初步判断如下：

- corpus 检索和 reranking 应当分开分析。两者耦合在一起时，粗粒度召回误差会掩盖 reranking 的真实收益。
- `Incomplete` 场景由于只有 1 个 GT，本身不适合作为重排能力的主要观察对象。
- wiki 路线暂时没有必要继续扩展，优先把现有 MRAG-Bench 设定做扎实。

## 讨论结论

后续优化方向不再局限于“找最像的图”，而是转向“按问题查询需要的信息”。核心思路是为 MagicLens 设计更好的 instruction / query，使检索目标更贴近问题本身。

可行方案包括：

- 人工设计 query / instruction，验证提示是否能显式引导检索到更有用的信息。
- 使用一个小模型根据 question 自动生成 MagicLens 的 query（instruction），作为带提示的通用查询模型。
- 尽量避免从头微调专门的查询模型，因为这可能会伤害模型的泛化性。
