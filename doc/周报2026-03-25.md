## 实验改进方案：多维度查询分解 RAG（Multi-Dimension Query Decomposition RAG）

### 一、核心思路

基于 04-02 分析报告的结论：MagicLens 直接用原始 question 做 instruction 时，query embedding 容易被开放式语义牵引到少数高响应原型图上（top-1 重复命中最高达 39 次），导致检索集合与 CLIP 大规模脱钩（909/1353 样本 top-5 零重合），但总体准确率反而低于 CLIP（47.97% vs 50.41%）。

**核心改进**：不再用单一 question 做 MagicLens instruction，而是用小模型将 question 分解为 N 个互补检索维度，每个维度生成一条精确的 retrieval instruction，分别检索后融合。

### 二、改进后的 Pipeline

```
(query_image, question)
       │
       ▼
┌──────────────────────────────────┐
│  小模型 / API 生成 N 个维度指令   │
│  d1: identity-preserving         │
│  d2: attribute-seeking           │
│  d3: complementary-view          │
│  ...                             │
└──────────┬───────────────────────┘
           │
     ┌─────┼─────┐
     ▼     ▼     ▼
  MagicLens  MagicLens  MagicLens
  top-K(d1)  top-K(d2)  top-K(d3)
     │     │     │
     └─────┼─────┘
           ▼
    Fusion / Re-rank
    (RRF / Score-sum / Voting)
           │
           ▼
    Final top-K images + query_image
           │
           ▼
        LLaVA 回答
```

### 三、为什么这样设计

1. **解决原型偏置问题**：单一 question 过于宽泛，导致 MagicLens 的 instruction embedding 倒向少数语义原型。拆成多维度后，每个维度的 instruction 更具体、更有约束力。
2. **利用维度互补性**：不同维度检索到的图片在信息层面互补（例如 identity 维度保证物种/品类不跑偏，attribute 维度找问题直接相关的属性图，complementary-view 补足角度信息）。
3. **自适应融合**：同一张图如果在多个维度都排名靠前，说明它同时满足多个检索需求，应优先选取。这正是周报里「image1（1,1,2,4,-1）score」想法的形式化。
4. **保留 MagicLens 优势场景**：在 Incomplete（17:7）和 Temporal 场景上 MagicLens 已经优于 CLIP，多维度检索能进一步放大这些优势。

### 七、第二数据集选型：候选分析与推荐

#### 7.1 当前系统的兼容性约束

选择第二数据集的前提是与当前 pipeline 兼容，核心约束如下：

1. 每样本 = `query_image` + `question`（MRAG-Bench 还有 A-D 选项）
2. 从一个**图像语料库**中检索 top-K 图片作为证据
3. 将 query_image + 检索图喂给 LLaVA 生成答案
4. 评估 = 准确率（按场景细分）
5. 核心主张 = 检索改进 → 准确率提升

一个"兼容"的第二数据集至少需要：有 query_image + question 输入、能构建图像语料库做检索、评估可量化检索带来的收益。

#### 7.2 五个候选数据集深度分析

##### (1) MRAMG-Bench（SIGIR 2025）

**数据格式**：JSONL，含 4,346 篇图文混合文档 + 4,800 个 QA 对 + 14,190 张图片

```json
{
  "id": "arxiv_001",
  "question": "What does Figure 3 in this paper show?",
  "provenance": [42, 87],
  "ground_truth": "Figure 3 shows <PIC> the attention heatmap...",
  "images_list": [301, 302]
}
```

- 文档内容中用 `<PIC>` 占位符标记图片位置，答案也是图文混合的
- 6 个子集：Wit / Wiki / Web / Arxiv / Recipe / Manual
- HuggingFace: `MRAMG/MRAMG-Bench`，GitHub: `MRAMG-Bench/MRAMG`

| 维度 | 兼容？ | 说明 |
|------|--------|------|
| 输入格式 | ⚠️ 部分 | 有 question + image，但 question 没有选项，检索目标是**文档**不是图片 |
| 检索目标 | ❌ 不兼容 | 检索的是图文混合文档，不是纯图片。MagicLens 是图像检索器，无法直接用 |
| 答案格式 | ❌ 不兼容 | 要生成图文混合答案，不是选 A-D 或短文本 |
| 评估方式 | ❌ 不兼容 | 用 Context Recall + Visual Recall + Image Precision + LLM 评判 |
| 适配工作量 | 🔴 巨大 | 需要改检索器（图片→文档）、改生成器（选择→生成）、改评估（全套新指标） |

**结论：虽然最"新"最"热"，但与我们的系统根本不在一个任务框架里。强行适配等于重新做一个项目。**

##### (2) RetVQA（IJCAI 2023）

**数据格式**：JSON，基于 Visual Genome 图片池

- 每个问题对应一组候选图片（有相关的 + 不相关的干扰项）
- 答案是开放式文本（短文本 + 分类标签混合）
- 数据通过 Google Drive 下载，图片来自 Visual Genome
- GitHub: `Abhiram4572/mi_bart`

| 维度 | 兼容？ | 说明 |
|------|--------|------|
| 输入格式 | ⚠️ 部分 | 有 question + image pool，但**没有单独的 query_image** |
| 检索目标 | ✅ 兼容 | 从图片池里检索 → 与我们从图像语料库检索一致 |
| 答案格式 | ⚠️ 部分 | 开放式文本，不是多选题，需要改 LLaVA prompt 和 extract 逻辑 |
| 评估方式 | ⚠️ 中等 | accuracy + fluency，accuracy 可复用，fluency 需额外指标 |
| 适配工作量 | 🟡 中等 | 需下载 Visual Genome（大），改 data loader，改评估 |

**致命问题：没有 `query_image`。** RetVQA 的设定是"给一个问题 + 一堆图，从中找答案"，而我们是"给一张 query 图 + 问题，从语料库检索辅助图"。核心交互模式不同，MagicLens 的 instruction-aware image retrieval 无法施展。

**数据格式**：JSONL

```json

  "data_id": "oven_entity_train_00000000",

  "entity_id": "Q1141409",
  "entity_text": "Dassault Falcon 900"
```

- 600 万个 Wikipedia 实体作为答案空间
- 输入 = 图片 + 文本查询 → 输出 = Wikipedia 实体 ID
- GitHub: `open-vision-language/oven`

| 维度 | 兼容？ | 说明 |
|------|--------|------|
| 输入格式 | ✅ 兼容 | image + question，与 MRAG-Bench 一致 |
| 检索目标 | ⚠️ 勉强 | 原始任务是实体链接，不是图片检索 |
| 答案格式 | ❌ 不兼容 | 答案是 600 万实体之一，不是多选题或短文本 |
| 评估方式 | ❌ 不兼容 | 实体匹配精度 |
| 适配工作量 | 🔴 巨大 | 任务本质是实体识别/链接，不是视觉问答 |

**结论：规模虽大但任务性质完全不同，不适合。**

| **RetVQA** | IJCAI 2023 | ⚠️ 无 query_image | ✅ | ⚠️ | 🟡 中 | ★★★ |
| **MRAMG-Bench** | SIGIR 2025 | ⚠️ | ❌ 检索文档 | ❌ | 🔴 大 | ★★ |
| **WebQA** | CVPR 2022 | ⚠️ 无 query_image | ⚠️ 图文混合 | ⚠️ | 🟡 中 | ★★ |
| **OVEN** | ICCV 2023 | ✅ | ⚠️ | ❌ 实体链接 | 🔴 大 | ★★ |

#### 7.4 最终推荐：InfoSeek（EMNLP 2023）

**推荐理由**：

1. **管线几乎原样复用**：输入就是 `image + question`，与 MRAG-Bench 一致。只需把 `iter_bench_queries` 里的 A-D 选项逻辑去掉，LLaVA prompt 从"选择题"改成"直接回答"，评估从 `choice == gt_choice` 改成 `answer in answer_eval` 的字符串匹配。核心的 MagicLens 检索 + 多维度查询分解完全不用改。

2. **检索增强有直接收益**：InfoSeek 的设计本意就是"光看图不够，需要外部知识"。96% 的问题普通人不查资料答不出来。多维度检索如果能找到更好的参考图，准确率提升的故事非常有说服力。

3. **与 MRAG-Bench 形成漂亮互补**：
   - MRAG-Bench = 视觉识别场景（角度/遮挡/变形/不完整），多选题，16K 图
   - InfoSeek = 知识密集场景（历史/地理/生物细粒度属性），开放问答，100 万+ 样本
   - 两个数据集一起能论证"多维度检索在不同任务类型上都有效"

4. **适配代码量极小**（约 35 行改动）：
   - `iter_bench_queries` 改为读取 InfoSeek 格式（~20 行）
   - `extract_choice` 替换为 `match_answer`（~10 行）
   - LLaVA prompt 去掉选项提示（~5 行）

5. **MRAMG-Bench 为什么不选**：虽然名字带"RAG"且最新，但它的"检索"是检索图文文档、"生成"是生成图文混合答案，与我们的纯图像检索 + 问答管线根本不在一个框架里，强行适配等于从头做另一个项目。
